# 个人生活平台 v1 — 需求与技术方案

- 版本：v1.0（第一阶段）
- 状态：已定稿，作为后续实现的**唯一依据**
- 受众：实现者（前端）、测试者、发布者
- 配套文档：`docs/data-schema.md`（JSON 数据格式权威定义）

---

## 1. 背景与目标

### 1.1 背景
需要一个属于自己的「个人生活平台」：既能看日历，又能记录每天的所见所得，并且**公网可访问、无需服务器、无需登录、零维护成本**。

### 1.2 第一阶段目标（v1）
用**最简单可用**的形态先跑通「记录 → 展示 → 公网可访问」这条最小链路，验证形态是否好用，再迭代扩展。

**v1 必须做到：**
1. 一个静态页面，双击本地 `index.html` 就能打开使用；
2. 顶部一个**月历视图**，能看到当月每一天，有记录的日期有可见标记；
3. 点击某一天，下方/右侧**当日记录面板**展示该天的记录（标题、备注、标签）；
4. 记录数据来自仓库内的 `data/entries.json`，**前端只读**；
5. 推送到 GitHub 仓库后开启 GitHub Pages，公网可直接访问（子路径 `/<repo>/` 下正常工作）。

**v1 明确不做（防范围蔓延）：**
- ❌ 不做站点内新增/编辑/删除（v2）
- ❌ 不做后端、数据库、账号体系、登录
- ❌ 不做构建工具链（不给 webpack/vite/tsc/包管理器）
- ❌ 不做第三方运行时依赖（框架、UI 库、CDN 资源）
- ❌ 不做习惯/健康/财务等多个生活模块（v3）
- ❌ 不做搜索、统计图表、导出、提醒、移动端 App

### 1.3 非目标（本阶段永远不做的）
- 用户系统与权限（这是单人自用工具）
- 数据加密、隐私合规审计
- 高并发、可用性 SLA

## 2. 术语表

| 术语 | 含义 |
|---|---|
| 条目 / entry | 一条每日记录，对应 `data/entries.json` 中 `entries` 数组的一个元素 |
| 记录日 / entry date | `entry.date` 字段，格式固定 `YYYY-MM-DD`，**本地日历日期**，不带时区 |
| 空日 / empty day | 当月某一天，在 `entries` 中没有对应 `date` 的记录 |
| 有记录日 | 当月某一天，在 `entries` 中**至少有一条** `date` 与之相等的记录 |
| 选中日 / selected date | 用户当前在日历上点击选中的日期，决定右侧记录面板展示哪一天 |
| 今日 / today | 运行时的本地系统日期（用于默认选中与高亮） |
| 资源根 | 页面引用的所有本地资源的基准路径，v1 固定为 **相对当前 URL 的 `./`** |

## 3. 站点结构（文件树）

v1 的仓库结构**固定**如下，文件名与路径不得更改（下游实现、测试与发布均依赖此约定）：

```
<repo-root>/
├── index.html                 # 唯一页面：月历 + 当日记录面板
├── assets/
│   ├── style.css              # 唯一样式表
│   └── app.js                 # 唯一脚本：加载数据、渲染日历与记录面板
├── data/
│   └── entries.json           # 唯一数据源（v1 只读）
├── docs/
│   ├── requirements.md        # 本文档
│   └── data-schema.md         # 数据格式定义
└── README.md                  # 说明如何本地打开、如何新增记录、如何发布
```

**硬性约束：**
- 只有 `index.html` 一个 HTML 页面；v1 不做多页面、不做路由。
- 只有 `style.css` 与 `app.js` 两个资产文件；不得额外拆分出模块文件。
- `data/entries.json` 是**唯一**数据来源；不得内置重复的备用数据副本。
- 仓库中**不得出现** `package.json`、`node_modules/`、构建产物目录、锁文件。
- 不得引入任何 `<script src="https://...">` 或 `<link href="https://...">`（外链字体、CDN、图标库一律禁止）。

### 3.2 区域能力要求

**A. 页头（Header）**
- 显示站点名称（固定文案：`个人生活平台`）。
- 显示当前展示的年月，格式 `YYYY 年 M 月`（月份不补零）。
- 提供「上一月」「下一月」两个可点击控件；点击后日历区按自然月滚动（跨年正确，如 2025-01 → 2024-12）。
- 提供「回到今天」能力（可放在页头或日历区，v1 允许以低成本方式实现；非阻断项）。

**B. 日历区（Calendar）**
- 表格化月历，**周一为第一列**，周日为最后一列（表头顺序：一 二 三 四 五 六 日）。
- 必须显示上月/下月的补位日期以填满整周，补位日期需视觉弱化（置灰）且**不可被选中为「当前月记录」**。
- 每月首日与末日的计算必须基于真实公历规则（含闰年、大小月）。
- **有记录日**必须有可见标记（圆点或底色），标记必须在不依赖颜色的前提下也可辨识（例如同时改变边框/加粗），以照顾色觉障碍。
- **今日**必须有独立的视觉标识（例如加粗边框），与「选中日」「有记录日」的样式互不冲突，三者可同时出现。
- 点击任意当月日期即将其设为**选中日**并刷新记录面板；选中态必须明显。

**C. 记录面板（Day Panel）**
- 面板标题显示选中日的日期，建议格式 `YYYY-MM-DD`（与数据字段一致，便于对照）。
- 选中日**有记录**时：按数据顺序列出该日全部条目，每条展示 `title`、`note`（可多行）、`tags`。
- 选中日**无记录**时：显示明确的空态文案（例如 `这一天还没有记录`），并提示新增方式（指向 `docs/requirements.md` 第 4 节 / README）。
- 面板内容随选中日切换而整体刷新，不得残留上一天的条目。
- 同一天存在多条记录时，v1 按 `entries` 数组顺序展示（不排序），稳定且可预测。

**D. 页脚（Footer，可选但推荐）**
- 显示数据条目总数。
- 数据加载异常时，此处或页面顶部必须给出可见错误提示（见 3.4）。

### 3.3 首次加载与默认状态
1. 页面加载后立即异步读取 `./data/entries.json`。
2. 日历默认展示**今日所在月**。
3. 默认选中**今日**：若今日所在月与展示月一致，则选中今日并展示其记录（可能是空态）。
4. 若今日不在展示月（例如用户切月后再刷新页面，行为仍以「今日所在月」为准），上述规则优先级高于任何记忆状态。
5. v1 **不要求**记住用户上次浏览的月份（允许但不要求；若实现则必须用 `localStorage` 且失败时静默降级）。

### 3.4 加载失败与异常降级（必须实现）
| 场景 | 期望行为 |
|---|---|
| `entries.json` 请求失败（404 / 网络错误） | 页面主体仍可渲染；日历可正常翻月；记录面板显示「数据加载失败」提示；页脚显示错误原因摘要 |
| JSON 解析失败（语法错误） | 同上，提示需明确指出「数据文件格式错误」 |
| `entries` 字段缺失或不是数组 | 视为 0 条记录，提示「数据格式不符合预期」 |
| 单条记录字段缺失/类型错误 | **跳过该条**并在控制台输出警告，不得因单条脏数据导致整页白屏 |
| `date` 值不是合法 `YYYY-MM-DD` | 跳过该条并在控制台输出警告 |
| 在 `file://` 下用 `fetch` 失败 | 必须给出明确提示：「请通过本地 HTTP 服务打开，或按 README 说明操作」，不得静默空白 |

> **已知技术约束（重要）**：浏览器对 `file://` 协议下的 `fetch()` 普遍存在 CORS 限制，直接双击 `index.html` 时**可能**读不到 `data/entries.json`。v1 的处置方式是：仍然采用 `fetch` + 明确错误提示；同时在 `README.md` 中提供一行本地 HTTP 服务的启动方式（如 `python -m http.server`），并说明「双击打开」在部分浏览器下受限。此为**已接受的已知限制**，实现者不得因此引入构建工具或内联数据副本。

### 3.5 响应式与可访问性
- 桌面优先；在窄屏（≤ 720px）下日历与记录面板改为**上下堆叠**（日历在上）。
- 所有交互控件必须可用键盘操作（日格为可聚焦元素，支持 Tab 到达 + Enter/Space 触发）。
- 交互控件需有可读的文本标签或 `aria-label`（例如 `6 月 14 日，有记录`）。
- 日历使用语义化表格结构，表头为列标题。
- 文本与背景对比度满足 WCAG AA 基本要求；不得仅靠颜色传达「有记录」这一信息。

## 4. 存储策略

### 4.1 v1：只读
- 前端**只读取** `./data/entries.json`，绝不写回仓库文件。
- 页面**不得提供**任何新增/编辑/删除 UI（这是 v2 的范围）。
- 不得存在任何写入请求（无 `POST`、无 `PUT`、无服务端）。

### 4.2 记录如何新增（v1 的实际操作方式）
v1 采用**手工编辑 JSON 文件**的方式新增记录，流程如下（README 必须原样说明）：

1. 在本地用编辑器打开 `data/entries.json`。
2. 在 `entries` 数组末尾追加一个对象，字段见 `docs/data-schema.md`：
   ```json
   { "date": "2025-06-15", "title": "今天的标题", "note": "备注内容", "tags": ["生活"] }
   ```
3. **注意 JSON 语法**：数组元素之间用逗号分隔，最后一个元素后面**不能有逗号**；字符串中的换行必须写成 `\n`，双引号必须转义为 `\"`。
4. 保存文件后用浏览器刷新页面验证；可在控制台看到记录总数。
5. 提交并推送到 GitHub，Pages 站点将在数分钟内自动更新。

> 为了降低手写 JSON 的出错率，`docs/data-schema.md` 提供了完整的合法示例片段，可直接复制修改。

### 4.3 localStorage 草稿（可选增强，写入后仍为 v2 范围）
- v1 **不要求**实现 localStorage 草稿功能。
- 若后续（v2）引入，必须遵守：localStorage 仅作为**未提交草稿**的暂存区，键名固定为 `life-platform:draft:v1`，其内容需与 `data-schema.md` 中的条目结构保持一致，并显示「未发布」的明确提示。
- v1 阶段 localStorage 的唯一允许用途是「记住上次浏览月份」（可选项），且必须 try/catch 静默降级。

### 4.4 数据体积与性能约束
- `entries.json` 预期规模：单人 10 年记录 ≈ 3650 条，文件 < 2 MB。
- 因此 v1 **不需要**分页、索引、虚拟滚动；一次性全量加载即可。
- 解析后建议在内存中按 `date` 建索引（`Map<date, entry[]>`），保证月历渲染与切换为 O(记录数)。

## 5. GitHub Pages 发布约束（必须全部满足）

1. **纯静态**：站点只有 HTML/CSS/JS/JSON，无服务端逻辑、无运行时环境要求。
2. **无构建步骤**：仓库中的文件**就是**发布内容；推送即发布，不存在 `dist/` 等中间产物。
3. **相对路径铁律**：
   - 所有资源引用必须是**相对路径**，且必须以 `./` 或 `../` 开头。
   - ✅ 正确：`./assets/style.css`、`./assets/app.js`、`./data/entries.json`
   - ❌ 错误：`/assets/style.css`、`/data/entries.json`（绝对值会指向域名根，在 `https://<user>.github.io/<repo>/` 下必然 404）
   - ❌ 错误：`assets/style.css`（省略 `./` 虽在实际中可用，但为保持一致性，统一要求写 `./`）
4. **子路径兼容**：站点必须能在 `https://<user>.github.io/<repo>/` 这一子路径下正常工作，不得假定站点位于域名根目录。
5. **无外链依赖**：不得引用任何外部 CDN、字体、图标、统计脚本（既保证离线可用，也避免发布环境差异）。
6. **文件名大小写敏感**：GitHub Pages 跑在大小写敏感的文件系统上，`data/entries.json` 与 `Data/Entries.json` 是不同文件。引用路径必须与实际文件名**逐字符一致**。
7. **数据处理**：`data/entries.json` 是静态资源，会被当作数据文件直接返回，无需特殊配置。
8. **发布流程（写入 README）**：
   - 推送到 GitHub 仓库的 `main` 分支；
   - 仓库 Settings → Pages → Source 选择 `Deploy from a branch`，Branch 选 `main`，目录选 `/ (root)`；
   - 等待 1–3 分钟，访问 `https://<user>.github.io/<repo>/`；
   - 若 404，依次检查：Pages 是否已启用、是否访问了带仓库名前缀的完整路径、文件名大小写是否一致、资源路径是否误用了绝对路径。
9. **缓存**：Pages 会缓存静态资源，更新数据后如看不到变化，使用强制刷新（Ctrl+F5）。README 需说明这一点。

## 6. 验收标准（v1 Definition of Done）

实现完成后，下列每一条都必须可在**已发布的公网 URL** 上验证通过：

| 编号 | 验收项 | 判定方式 |
|---|---|---|
| A1 | 页面可通过 `https://<user>.github.io/<repo>/` 打开，无 404 | 浏览器直接访问 |
| A2 | 打开后默认展示**今日所在月**，且今日被选中 | 视觉确认 |
| A3 | 日历以**周一为第一列**，表头顺序为「一 二 三 四 五 六 日」，且表头各列与其下方日期的真实星期一一对应 | 视觉确认 + 对照首行日期核对星期 |
| A4 | 有记录的日期显示可见标记；示例数据中的日期全部出现标记 | 对照 `entries.json` 逐一确认 |
| A5 | 点击有记录日期，记录面板列出该日全部条目（title/note/tags 齐全，含中文正常显示） | 点击验证 |
| A6 | 点击无记录日期，面板显示空态文案，且**不残留**上一天的条目 | 连续点击切换验证 |
| A7 | 翻月按钮工作正常；跨年（2025-01 ↔ 2024-12）正确；闰年 2 月为 29 天（例：2024-02） | 点击验证 |
| A8 | 窄屏（≤720px）下日历与面板上下堆叠，无横向滚动条 | 浏览器缩放/DevTools |
| A9 | 浏览器控制台**无报错**（`console.error` 为空） | DevTools Console |
| A10 | 页面在离线（断网）状态下依然完整可用（证明无外链依赖） | 断网刷新 |
| A11 | 资源路径均为相对路径，且子路径部署下 CSS/JS/JSON 全部 200 | Network 面板 |
| A12 | `data/entries.json` 至少含 3 条以上示例记录，且覆盖「有记录日」与「无记录日」两种展示情形 | 阅读文件 |
| A13 | 仓库中不存在 `package.json` / `node_modules/` / 构建产物 | 目录检查 |
| A14 | `entries.json` 被人为改坏（删掉一个逗号）时，页面给出「数据文件格式错误」提示而非白屏 | 手工破坏后验证，验证完恢复 |

## 7. 迭代路线图

> 本节只描述方向，v2/v3 **不在本任务范围内**，不得提前实现。

### v1 — 日历 + 每日记录展示（当前阶段）
- 单页静态站，月历 + 当日记录面板
- 数据来自 `data/entries.json`，**只读**
- 手工编辑 JSON 新增记录
- 发布到 GitHub Pages，公网可访问
- 交付物：`index.html`、`assets/`、`data/entries.json`、`README.md`、`docs/`

### v2 — 站点内新增 / 编辑记录（下次迭代）
目标：不再需要手改 JSON。
- 记录面板新增「新增 / 编辑 / 删除」入口，提供表单（日期、标题、备注、标签）
- 数据持久化方案二选一，届时决策：
  - **方案 A（推荐起步）**：localStorage 本地存储 + 导出/导入 JSON 文件（用户手动把导出的 JSON 覆盖回仓库再推送）
  - **方案 B**：接入 GitHub API（Personal Access Token）直接提交 `entries.json`，实现「网页里写、自动提交」
- 引入草稿与已发布状态区分，避免误覆盖仓库数据
- 标签补全与日期选择器
- 数据量增长后的按月懒加载
- 交付物增量：编辑表单、存储抽象层（先 localStorage，后可替换为 GitHub API）

### v3 — 多类生活模块
目标：从「日记」升级为「个人生活平台」。
- 新增模块：**习惯打卡**（连续天数、完成率）、**健康**（体重/睡眠/运动）、**财务**（收支台账）
- 数据分文件管理（如 `data/habits.json`、`data/health.json`、`data/finance.json`），各自独立 schema，`schemaVersion` 独立演进
- 顶层导航切换模块；模块内复用 v1 的日历与列表组件
- 引入统计视图（趋势图、月度汇总）
- 数据迁移工具：老 `entries.json` 平滑升级，schema 版本迁移脚本
- 交付物增量：多数据源、模块路由、图表渲染（仍可保持零依赖，用原生 SVG 绘制）
